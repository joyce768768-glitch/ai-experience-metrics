一
CHAPTER 01 · THE FULL PIPELINE

闭环全景：一条流水线，三条反馈回路

闭环不是抽象的循环图，而是一条有工单、有产出物、有通过标准的流水线。正向八站；任何一站不达标，都沿反馈回路退回重做。

PIPELINE

正向八站 × 反馈三路

EVERY STAGE HAS AN ARTIFACT & A GATE

GATE-1 · 回归门

回归未通过 → 退回「改进」。禁止带病上线，也禁止「局部修好、全局变差」的改动通过。

GATE-2 · 实验门

A/B 无效或护栏指标破线 → 退回「归因」。假设错了就重立假设，而不是调参数碰运气。

GATE-3 · 监控门

全量后持续监控，新问题流回「发现」。这一路让流水线成为真正的闭环，而不是一次性项目。

二
CHAPTER 02 · TEST DATASETS

测试数据集：六库一体

没有数据集，闭环就没有「再次测试」的地基——所有改进都无法证明有效。六个库各司其职，共同构成回归与评测的底座：

SET-01
标准任务集
GOLDEN SET

每类任务 30–50 条有明确验收标准的代表性任务，附参考答案。用于例行回归与版本对比。

频率：每次改动全量跑 · 难度标定 L1–L3
SET-02
边界与对抗集
EDGE & ADVERSARIAL

歧义指令、矛盾约束、超长上下文、罕见输入、格式陷阱。专测「意外」，防体验在边角崩塌。

频率：每周巡检 · 人工构造 + 自动变异
SET-03
负例集
NEGATIVE SET

历史已修复失败模式的原始样本。用于验证「旧病未复发」——回归的核心武器。

频率：每次改动必跑 · 只增不减
SET-04
Badcase 回归集
BADCASE REGRESSION

每个关闭的 badcase 自动转化入库：原始输入 + 复现环境 + 通过标准。是负例集的增量来源。

频率：关单即入 · 永久保存
SET-05
红队集
RED TEAM SET

安全、越权、隐私、资金类攻击场景。专供安全违规率（M-04）的主动探测。

频率：季度红队演练 + 每次安全相关改动
SET-06
基线数据库
BASELINE DB

人工完成同类任务的耗时与质量基线。时间节省率、质量改善幅度的分母来源。

频率：季度刷新 · 按任务类型分层
建集五条纪律
  • 验收标准事前写死——先定标准再跑测试，禁止跑完再解释结果。
  • 每条样本双维标注——任务难度（L1–L3）× 考察能力（理解 / 规划 / 工具 / 生成 / 表达），归因时可以直接下钻。
  • 版本化管理——数据集像代码一样有版本号（如 GOLDEN v2.3），每次回归记录所用版本，保证结果可比。
  • 季度体检——过期样本（不再代表真实任务分布）降权或淘汰，防止数据集僵化。
  • 规模克制——标准任务集保持精而准（每类 ≤ 50），回归速度比覆盖广度更影响闭环速度。
三
CHAPTER 03 · BADCASE LIFECYCLE

Badcase 管理：一个状态机

Badcase 的定义采用暴露率视角：用户实际感知到的失败才算数（模型内部错误被拦截的不计）。每个 badcase 是一个工单，沿状态机流转，关单的唯一条件是回归通过 + 入库。

新报→ 确认→ 归因→ 修复中→ 回归验证→ 关闭 · 入库
S1 / S2 / S3 严重度

S1 不可逆损失或资金风险（24h 内归因）；S2 功能不可用（72h）；S3 体验瑕疵（周内）。

必填打标字段

现象描述 / 任务上下文 / 复现输入 / 影响面 / 初判类别。缺字段的工单不进评审会。

重开机制

关闭后同类问题复发 → 自动重开并升一级严重度。复发是比新增更危险的信号。

三条纪律：每周固定 badcase 评审会（逐条过 S1/S2）；禁止「无法复现」直接关单——必须记录环境与输入留档；S1 工单跨夜未归因自动升级管理层。
四
CHAPTER 04 · ROOT CAUSE ANALYSIS

归因分析：五层下钻 + 五类根因

归因的纪律是只回答「为什么发生」，不回答「怎么改」——方案留给改进环节。用五层下钻把现象逐层翻译，最后落到五类根因之一：

五层下钻（从现象到责任）
L1 现象层
用户看到了什么错？「生成的报告漏掉了第三季度数据」用用户语言记录，不掺技术判断
L2 任务层
哪类任务、哪一步？「数据汇总类任务 · 数据读取之后、汇总生成之前」关联分层维度，便于统计归类
L3 环节层
流水线哪个环节产生偏差？「工具调用了错误的数据源参数」理解 → 规划 → 工具 → 生成 → 交付
L4 根因层
归入五类根因之一（见下表），引用证据：日志、重放记录、差分对比
L5 责任层
归属团队与优先级：算法 / 工程 / 设计 / 产品 / 数据——归因会开完直接派单
ROOT-A
意图理解错

没懂用户要什么：目标偏移、约束丢失、隐含需求漏判。

ROOT-B
计划执行错

懂了但做错：步骤遗漏、顺序错误、中途漂移、终态未验证。

ROOT-C
工具数据败

外部依赖失败：工具超时、数据源错误、接口变更、状态丢失。

ROOT-D
交互表达错

做对了但用户不知道/误解：进度不可见、结果难纠错、说明含糊。

ROOT-E
标准预期错

AI 做的没错，是验收标准不清或用户预期错位——改标准而非改系统。

三个下钻方法，按成本从低到高依次使用：

壹
重放复现

用原始输入在受控环境复跑，确认问题稳定可现。复现率 < 100% 时记录触发条件——「偶现」本身是重要线索。

贰
差分对比

找同类成功样本与失败样本逐项对比（输入结构 / 上下文长度 / 工具路径），差异点即嫌疑点。

叁
环节插桩

在嫌疑环节加临时日志或中间产物导出，观察中间状态。成本最高，但根因最硬。

归因报告一页纸：现象 → 复现步骤 → 根因（含证据）→ 影响面 → 修复建议 → 验证标准。归因完成的标志是「验证标准已写好」——它就是回归环节的输入。
五
CHAPTER 05 · FIX & IMPROVE

优化改进：对症下药 + 改动分级

每类根因对应固定的手段组合。改动的每个动作必须挂在假设上：「因为 X（根因），所以改 Y（手段），预期 Z 指标变化（验证标准）」——没有 Z 的改动不准上线。

根因对症手段主责方典型验证指标
意图理解错澄清策略优化 / 上下文增强 / 目标确认点 / 领域目标模板产品 + 设计目标对齐率 · 首次对齐轮数
计划执行错计划展示 / 步骤约束 / 关键节点自检 / 终态验证工程 + 产品步骤完成率 · 意图漂移率
工具数据败重试策略 / 降级方案 / 断点恢复 / 依赖巡检工程异常恢复率 · MTTR
交互表达错精准反馈控件 / 进度透明 / 纠错接口 / 不确定性标注设计纠错成功率 · 监督负担
标准预期错验收标准前置 / 期望管理 / 任务说明优化产品首次交付通过率 · 纠错次数
模型能力不足提示词工程 / few-shot / 模型升级 / 针对性微调算法结果可用率 · 输出方差
HOTFIX · 24H
紧急通道

S1 badcase、安全红线相关。跳过排期直接修复，但回归与入库一个不少——快不等于糙。

REGULAR · 排期内
常规改动

S2/S3 与体验优化项。进迭代排期，随版本走完整流水线：改进 → 回归 → 灰度。

PROJECT · 立项
专项治理

同一根因反复出现 > 3 次，说明不是补丁问题而是结构问题——立项做系统性重构（如权限模型、记忆架构）。

单变量纪律：一次实验只改一个变量。多改动并行时，先拆分再实验——否则验证环节无法归因，等于白做。
六
CHAPTER 06 · REGRESSION

再次测试：两级回归，一道闸门

回归回答一个问题：修好了旧问题，且没有制造新问题。两级测试，缺一不可：

LEVEL 1 · 专项回归
这个 badcase 真的修好了吗
  • 原始失败输入 100% 复跑通过
  • 同模式变体 5–10 条（换数据 / 换措辞 / 换顺序）通过
  • 相邻能力点的边界样本抽查
LEVEL 2 · 全量回归
别处没有被误伤吗
  • 标准任务集全量：成功率不低于基线 −1pp
  • 负例集 + 历史回收集全量：零复发
  • 关键质量分（可用率 / 方差）无显著劣化
通过标准（Gate-1）：专项 100% + 全量达标，双过才放行。通过后立即做两件事：badcase 转入回收集（永久防复发）、工单可关单。离线回归通过 ≠ 上线验证——真实流量要靠下一站的灰度与 A/B。
七
CHAPTER 07 · A/B TESTING

A/B 实验：七步一个实验

回归证明「不更坏」，A/B 证明「更好」。不是所有改动都值得 A/B——有效果假设、多方案择优、或有风险争议的改动才进实验；纯文案与纯修复走灰度监控即可。

01
立假设
一句话写清：因为（根因）改了（手段），预期（主指标）变化（方向与幅度）。写不出假设的改动退回。
02
定指标
主指标 1 个（对准假设）+ 护栏 2–3 个（安全违规率、耗时、满意度——护栏破线即终止，无论主指标多好看）。
03
设计分流
按用户还是任务分流？改动影响单任务行为用任务分流，影响会话体验用用户分流。确保两组任务难度分布一致。
04
算样本量
按最小可检测效应（MDE）与基线水平估算，置信度 95%、功效 80%。样本不足的实验宁可不跑——测不出差异比不测更浪费。
05
运行观察
至少覆盖一个完整周期（含工作日与周末），消除周内效应。期间冻结其他相关改动，保证归因干净。
06
判定
统计显著 + 业务意义（提升幅度值得改动的复杂度）+ 护栏全绿，三者同时满足才算赢。
07
决策落库
全量 / 回滚 / 迭代三选一。无论输赢，实验记录入库——失败的假设同样防止后人踩坑。
灰度阶梯：1% → 5% → 25% → 50% → 100%，每级观察 24–48h，任一级出现异常立即回滚。高风险改动（权限、资金、记忆写入）必须走满阶梯；低风险可压缩至两级。
八
CHAPTER 08 · PROBLEM SOURCES

持续找问题：六个哨点

闭环的燃料是「发现问题」。只有用户投诉一条渠道的团队永远在救火。六个哨点，从被动到主动——成熟团队的主动发现占比应 ≥ 50%：

PASSIVE · 被动
用户反馈与客服

一键反馈、差评、客服工单。最真实但最滞后，且自带幸存者偏差——沉默的流失用户不在这里。

节拍：实时进队列 · 周度汇总
ACTIVE · 主动
指标监控告警

12 个核心指标的阈值触发（VOL.04 触发机制）。机器值守，异常自动进诊断队列。

节拍：实时 · S1 当日响应
ACTIVE · 主动
真实任务巡检

每周从线上抽样真实任务（含长尾场景）人工评审。专抓「用户没报但确实差」的沉默问题。

节拍：每周 · 固定抽样配额
ACTIVE · 主动
用户研究

月度访谈 + 可用性测试，专挖行为数据看不见的动机、误解与替代方案。 badcase 的上游富矿。

节拍：月度 · 覆盖新老用户
ACTIVE · 主动
红队与众测

季度红队演练攻击安全与边界；新功能上线前组织众测。主动制造极端情况。

节拍：季度 + 大版本前
ACTIVE · 主动
数据挖掘

对会话日志做聚类，找出「高纠错率」「高放弃率」「长时间停顿」的异常模式——用户用脚投出的坏案例。

节拍：双周跑批 · 产出聚类报告
九
CHAPTER 09 · SOLIDIFY & HEALTH CHECK

沉淀资产与闭环自检

循环每转一圈，必须留下五种资产中的至少一种，否则这次闭环只是救火：

关单前必须回答：这次循环沉淀了什么？
  • 评测用例——badcase 及其变体进入回收集 / 负例集，永久防复发。
  • 设计规范——验证有效的交互模式写入规范，同类场景不再从零设计。
  • 验收标准——标准不清类根因（ROOT-E）修订进 checklist，前置到任务开始。
  • 阈值修订——本轮发现阈值不合身（误报 / 漏报），同步更新触发规则。
  • 实验记录——成败假设入库，供后续实验检索，避免重复试错。

每月用五问为闭环本身体检——不达标项改的是流程，不是产品（元循环）：

闭环健康度 · 月度五问达标线不达标时改什么
badcase 从确认到关闭的中位时长< 2 周查瓶颈站：归因积压加人力，回归排队提优先级
badcase 复发率（关闭后 30 天内重开）< 10%复发 = 修复不彻底：查回归标准是否太松
回收集规模趋势逐季上升下降说明关单没入库——收紧关单条件
实验命中率（假设被验证的比例）趋势上升命中率低 = 归因质量差，回炉第四章方法
主动发现问题占比≥ 50%被动占比高 = 哨点失守，加强巡检与数据挖掘
CODA · 结语

指标告诉你哪里疼，闭环负责治好它并记住这次病历。数据集是地基，badcase 是病历，归因是诊断，改进是处方，回归是复查，A/B 是对照试验，沉淀是把病历写进教科书——当每一次失败都变成防复发的用例，产品就获得了只会越来越好的体质。这就是闭环的全部意义：不是不出错，而是同样的错，绝不出第二次。
