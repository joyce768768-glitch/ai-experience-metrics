全卡 6 · 标准卡 6 · 简卡 6 18 CARDS · DELEGATE / EXECUTE / RECOVER / SUPERVISE

六维重排第四卷，也是体量最大的一卷（18 卡）。忠于源框架第四维度「Agent 执行体验」整卷重建：用户把目标委托给 AI，让它规划、调用工具、执行并处理异常——这是 Agent 与聊天机器人的分界线。主字典卷已拆的端到端成功率、异常恢复率、监督负担归位；底层支撑指标（工具调用、输出稳定性、成本效率）与 Agent 四组（自主委托、多步长程、人机协作控制、失败恢复）全部聚合。

本维度的底层判断：自主完成率越高 ≠ 体验越好——中等自主性、保留干预通道的方案在效率与控制偏好之间更平衡。执行体验同时回答四个问题：它能不能做完？用户知不知道它在做什么？能不能在关键节点介入？错了能不能不从头再来？

F-01

端到端任务成功率

END-TO-END TASK SUCCESS全卡 · 北极星锚点
定义
从目标输入到最终交付的全链路成功占比——单步成功不等于任务成功，验收标准必须事前定义。它是北极星「用户目标成功率」在体验面的落点。
目的
回答「用户委托的目标是否真正达成」——从目标输入到最终交付的全链路成功，而非单步成功。它是北极星「用户目标成功率」最直接的观测面，也是所有体验指标的锚点：其他指标异常时，最终都会反映在这里。
公式
任务成功率 = 满足全部验收标准的任务数 ÷ 纳入评测的任务总数。口径：验收标准必须事前定义；部分完成、用户中途放弃、降级完成均不计入成功。
评估标准
≥ 85% 健康70–85% 预警< 70% 危险
阈值必须按任务难度分层设定：低风险标准化任务的基线应显著高于开放式复杂任务。跨难度直接比较是本指标最常见的滥用。
数据来源
行为日志（任务状态机终态：完成 / 失败 / 放弃 / 接管）+ 客观评测（标准任务集的事前验收判定）+ 用户信号（显式验收动作：接受 / 重做 / 差评）。
数据埋点
事件 task_state（状态机终态 completed/failed/abandoned/takeover，属性 difficulty 难度、risk_tier、acceptance_result 验收判定）。采集端：编排层状态机日志（全量）+ 评测任务集跑批 + 显式验收动作埋点。
分层
任务风险等级（L0 只读 → L3 不可逆）× 任务难度（步骤数 / 依赖工具数）× 用户群体（新手 / 专家）× 时间窗（周 / 月）。
触发机制
周环比下降 > 5pp → 一级诊断，48 小时内归因报告（哨点：指标监控告警）；任一高风险任务层跌破危险线 → 立即触发专项复盘，相关功能降级评估。
改进闭环
失败任务聚类 → 四类归因（理解错 / 执行错 / 工具失败 / 环境异常）→ 分发给对应责任方修复 → A/B 实验验证 → 沉淀（失败样本转化为新评测用例，进入回归集）。
反指标
用「步骤成功率连乘」冒充端到端——90% 的十步连乘只剩 35%。gaming：把放弃任务移出分母（幸存者偏差）。配对监控：任务放弃率 + 验收标准事前覆盖率（多少任务的验收是先定义的）。

F-02

异常恢复率

FAILURE RECOVERY RATE全卡
定义
出错后恢复并最终完成的任务占比——系统成熟度试金石。首次成功靠运气，恢复率只能靠工程。配套观测平均恢复时间 MTTR。
目的
回答「失败后能否回到正轨」。系统成熟度的试金石：首次成功率靠运气也可能高，恢复率只能靠工程与设计能力。
公式
异常恢复率 = 出错后恢复并最终完成的任务数 ÷ 出现错误的任务数。配套口径：平均恢复时间 MTTR = 从失败发生到任务回到正轨的平均时长。
评估标准
≥ 70% 健康50–70% 预警< 50% 危险
同时约束 MTTR < 2 × 同类任务正常完成时间，两者任一超标都算预警。
数据来源
错误事件日志（类型 / 时点 / 上下文）+ 恢复路径追踪（自主恢复 / 用户介入 / 放弃）+ 断点保存与续跑记录。
数据埋点
事件 error_event（属性 type 工具失败/网络/模型拒绝/状态丢失、stage 发生时点）、recovery_path（属性 autonomous 自主恢复/user_intervention/abandon、mttr、retry_count）。采集端：错误日志 + 恢复路径追踪 + 断点续跑记录。
分层
错误类型（工具失败 / 网络 / 模型拒绝 / 状态丢失）× 发生时点（任务早期 / 中期 / 后期）——后期失败的恢复价值远高于早期，用户承受的沉没成本更大。
触发机制
MTTR 超过正常完成时间 2 倍 → 触发恢复机制专项（「错了不如重做」是体验灾难）；同一错误重复率 > 20% → 触发根因修复而非继续打补丁。
改进闭环
恢复失败样本 → 补断点保存 / 重试策略 / 回滚机制 → 混沌注入测试验证 → 沉淀（错误处理手册更新，错误模式进入故障演练库）。
反指标
用「重试次数多」冒充恢复力——盲目重试是烧钱不是恢复。gaming：把用户放弃的重灾区任务移出分母。配对监控：MTTR + 同一错误重复率（恢复是否修在根上）。

F-03

用户监督负担

USER SUPERVISION BURDEN全卡
定义
用户在任务总时长中用于监督（盯进度、查状态、等确认）的占比——Agent 价值的试金石。名义自主、实际监工 = 承诺未兑现。
目的
回答「用户是否仍需盯着 AI」。Agent 价值的试金石：如果名义上自主执行、实际上全程盯梢，工作只是从「做」变成了「监工」——Agent 就没有兑现承诺。
公式
监督时间占比 = 监督时间（盯进度 / 查状态 / 等确认）÷ 任务总时长。辅助指标：每任务进度查看次数、空闲等待中的主动刷新次数。
评估标准
< 20% 健康20–40% 预警> 40% 危险
长任务（> 30 分钟）单独设线：> 30% 即预警。
数据来源
页面焦点与停留日志 + 进度页 / 状态页访问事件 + 用户调研校准（区分「必要确认」与「不放心」）。
数据埋点
事件 attention_probe（页面焦点 / 停留，属性 view_target 进度页/状态页/日志、idle_refresh 空闲主动刷新）、confirm_wait（等待用户确认的阻塞时长）。采集端：客户端焦点埋点 + 通知点击 + 调研校准（区分必要确认与不放心）。
分层
任务时长 × 自主等级 × 用户角色。长任务是重点：监督负担与任务时长呈超线性增长。
触发机制
长任务监督占比 > 40% → 触发主动通知机制优化（关键节点推送 / 异常才打扰）。
改进闭环
高监督样本分析 → 找出用户缺什么信息（进度 / 中间产物 / 风险预警）→ 增加主动汇报点 → 验证监督占比下降 → 沉淀（「何时汇报、汇报什么」的沟通策略规范）。
反指标
用「通知发送量」冒充主动汇报——发了没人看是噪音不是减负。gaming：把用户主动查看（不放心）算成必要确认。配对监控：通知打开率 + 委托后安心度 · 本卷 L-06。

F-04

工具调用成功率

TOOL-CALL SUCCESS RATE全卡 · L4 第一因
定义
Agent 调用外部工具成功的比例——L4 执行力的第一因。工具失败是执行失败的最大单一来源，失败四分类定位是基本功。
目的
Agent 区别于聊天机器人的第一能力分界——能否把计划变成真实世界的动作。工具层失败会沿因果链逐级放大：工具调用成功率下降 → 执行失败率上升 → 用户接管增加 → 监督负担上升 → 满意度下降。它是 L4 技术驱动指标中的第一因，也是体验问题关联到工程侧的第一入口。
公式
成功率 = 参数正确且返回预期结果的调用数 ÷ 调用总数。口径：调用成功 × 结果正确两层都过才算——HTTP 200 但参数错 = 失败。拆两个子口径：工具故障（外部依赖问题）与调用错误（Agent 责任），归因走向完全不同。
评估标准
健康 ≥98%预警 95–98%危险 <95%
Agent 责任子口径单独要求 ≥99%——外部依赖可以原谅，Agent 自己参数幻觉不能。
数据来源
工具网关日志全量 + 参数校验埋点（禁止抽样，写类操作全量）。
数据埋点
事件 tool_call（属性 tool_id、result success/timeout/auth_fail/bad_request 四分类、retry_count、duration、fallback_used 降级方案）。采集端：编排层工具网关日志（全量）+ 超时与降级路径专项标记。
分层
工具类型（读 / 写 / 支付类）× 失败类型（超时 / 参数错 / 权限 / 依赖故障）× 时段。
触发机制
周环比 −2pp 或单工具失败率 >10% → 一级诊断（哨点：监控告警）；写类工具任何失败必须 100% 进 badcase 库。
改进闭环
归因（schema 描述不清 / 参数幻觉 / 工具版本漂移）→ 修复（工具描述重写、参数校验前置）→ 回归（专项 + 全量）→ 沉淀（工具描述规范入接入 checklist；失败样本入对抗测试集）。
反指标
用「调用次数多」冒充能力强——乱试工具是撞运气。gaming：把超时重试成功算首次成功。配对监控：单任务调用次数分布（异常膨胀 = 规划能力差）+ 降级方案使用率。

F-05

长程任务成功率

LONG-HORIZON COMPLETION全卡
定义
多步骤、跨时长任务的完成率——Agent 主场的真实考验。长程失败的主因是漂移与状态丢失，不是单步能力不足。
目的
多步骤、跨工具、长时间任务最终达成的比例——Agent 成熟度的总成绩单。用户对 Agent 的最终期待不是某一步漂亮，而是整件事办成。
公式
成功率 = 满足全部终态验收条件的长任务数 ÷ 纳入评测的长任务总数。口径：长任务 = ≥5 必要步骤或跨 ≥2 工具/应用；验收条件事前写死（闭环手册建集纪律一），禁止跑完再定标准。
评估标准
健康 ≥70%预警 50–70%危险 <50%
必须先按难度分层（步骤数 / 工具跨度），不同难度档之间禁止直接比较。
数据来源
标准长任务集（难度标定）+ 真实委托任务回溯标注。
数据埋点
事件 long_task（属性 step_count 步数、duration、milestone_checkpoints 各里程碑状态、drift_events 偏移事件、resume_count 续跑次数）。采集端：编排层长任务日志 + 里程碑核验点埋点。
分层
步骤数分档（5–10 / 10–30 / 30+）× 工具跨度 × 中断次数。
触发机制
任一难度分档环比 −8pp → 定位卡点层；与步骤完成率的差值扩大（步骤全做了但任务失败）→ 转执行顺序与输出质量归因。
改进闭环
归因五层下钻（现象→任务→环节→根因→责任）→ 修复 → 回归 → 沉淀（卡点任务入评测集；「步骤完成但失败」模式入归因知识库）。
反指标
用「长任务启动量」冒充长程能力——开了不算，跑完才算。gaming：把长任务拆短计入成功率。配对监控：任务偏航率 + 断点恢复成功率（长程两大死因）。
来源警示：步骤完成率不是长程任务成功率的替代指标——所有步骤都被执行，不代表执行顺序正确、输出质量合格或最终目标实现。两个指标必须并列监控，差值本身就是诊断信号。

F-06

重复执行率

REPEATED EXECUTION RATE全卡 · 红线域
定义
Agent 重复执行已完成动作或产出重复结果的比例——资源黑洞与信任杀手。用户看到「它在原地打转」的瞬间，委托信心归零。
目的
因状态丢失、重复调用或计划错误而重复执行的比例——长程执行中最阴险的失败：不只是浪费成本，对写类、支付、外发操作，重复执行本身就是事故（双倍下单、重复群发）。副作用场景划入红线域。
公式
重复执行率 = 发生重复执行的步次数 ÷ 总执行步次数。口径：带去重键且结果一致的幂等重试不计入；无去重保护的写操作重复单独统计为「危险重复数」。
评估标准
全量 <2%预警 2–5%危险 >5%
危险重复数（写类无保护）= 0 · 红线——一次也算事故。
数据来源
执行日志全量（调用指纹去重自动检测）+ badcase 回收。
数据埋点
事件 exec_fingerprint（动作序列指纹哈希，属性 repeat_count、wasted_tokens 浪费算力、cause 状态丢失/幂等缺失/死循环）。采集端：编排层序列指纹检测（全量）+ token 浪费核算。
分层
操作可逆性（读 / 可逆写 / 不可逆写）× 重复原因（状态丢失 / 重复调用 / 计划器循环）。
触发机制
危险重复数 ≥1 → S1 级 badcase，24h 内归因（闭环手册 badcase 状态机）；全量环比 +1pp → 一级诊断。
改进闭环
归因（状态未持久化 / 缺幂等键 / 计划器死循环）→ 修复（幂等保护、状态检查点）→ 回归（专项 + 全量）→ 沉淀（幂等规范入工具接入 checklist；重复模式样本入对抗测试集）。
反指标
用「任务重跑成功」冒充恢复——重跑成功掩盖了为什么第一次没成。gaming：把重复执行归入「主动重试」口径。配对监控：token 成本异常会话占比 + 用户手动接管率（打转逼人接管）。

CHAPTER 03 · STANDARD CARDS

标准卡 ×6：执行全链路

六张标准卡排成执行链路：断点续跑 → 跨工具接力 → 偏航监控 → 终态验证 → 委托 → 接管。

S-01

断点恢复成功率

RESUME SUCCESS RATE标准卡
定义
任务中断后从断点继续并完成的比例——长任务的生命线。能续跑的任务，用户才敢委托长事。
目的
中断后能否带着完整上下文继续任务——长任务的容错底线，直接决定用户敢不敢把大任务整段委托（委托前先想「崩了怎么办」）。
公式
恢复上下文并继续且最终完成的中断次数 ÷ 中断总数。
评估标准
健康 ≥85%预警 70–85%危险 <70%
数据来源
中断事件埋点 + 恢复会话抽样复测。

跨工具连续性

CROSS-TOOL CONTINUITY标准卡
定义
任务跨多个工具 / 系统执行时上下文与状态无损耗传递的比例——接力赛的交接棒质量。
目的
在不同工具与应用之间保持任务状态、参数和约束的能力——Agent 的「手」之间不能失忆。单工具各自成功、拼起来任务失败，是长程任务失败的隐蔽主因。
公式

评估标准

S-03

任务偏航率 / 意图漂移率

DRIFT & DEVIATION标准卡 · 双口径
定义
执行路径偏离既定计划或用户目标的比例——长任务的隐性病。双口径：意图面（漂向了别的事）联动卷一，执行面（步骤跑偏）留在本卷。
目的
双口径盯「走偏」：意图漂移 = 多轮执行偏离原始目标（理解层）；任务偏航 = 执行偏离有效计划或约束（执行层）。同一现象的两层归因——分开测，才能定位该改模型理解还是改任务规划。
公式
各自 = 偏离任务数 ÷ 对应任务总数。偏离判定以有效目标 / 计划基准为准；用户主动改向不计入（那是目标更新，不是漂移）。
评估标准
健康 <5%预警 5–12%危险 >12%
数据来源
评测集（预埋基准计划）+ 委托任务回溯标注。
数据埋点
事件 plan_deviation（属性 deviation_step 偏移步、type 目标漂移/步骤偏航/范围蔓延、severity、self_corrected 自纠）。采集端：计划 - 执行比对（编排层）+ 里程碑产物核验。
分层
轮数 / 步数分档 × 偏离类型（目标 / 约束 / 范围）。

S-04

终态验证覆盖率

FINAL-STATE VERIFICATION COVERAGE标准卡
定义
任务结束时有客观终态核验（而非模型自评）的比例——「说做完了」不等于「做完了」。
目的
Agent 对最终交付物是否做了必要验证——「做完了」和「确认做对了」是两种能力。无验证的完成等于把验收成本转嫁给用户，直接推高监督负担。
公式
完成必要终态验证的任务数 ÷ 应验证任务数。
评估标准
高风险任务 =100%全量健康 ≥90%预警 <90%
数据来源
执行日志验证步骤核查 + 评测集。
数据埋点
事件 final_verify（属性 verify_method 测试/断言/外部核对/模型自评、pass、gap 未覆盖原因）。采集端：编排层验收钩子埋点。
分层
交付物类型（代码 / 文档 / 操作结果）× 风险等级。

S-05

委托意愿

DELEGATION WILLINGNESS标准卡
定义
用户主动把任务交给 AI 而非自己做的比例与意愿强度——信任的行为表达。意愿看的是「选它」的瞬间，不是用完的评价。
目的
用户愿意把哪类任务交给 Agent——行为化的信任刻度，是所有 Agent 能力指标在用户心中的加权总分。意愿结构（愿意什么 / 不敢什么）比均值更有信息量。
公式
周期内实际委托的同类任务数 ÷ 该类任务发生总数（行为口径为主，问卷意愿分为辅）。
评估标准
核心任务类 ≥60%预警 40–60%危险 <40%
必须按任务类分层判级，跨类比较无意义。
数据来源
行为埋点（委托 vs 手动完成）+ 季度问卷。
数据埋点
事件 delegation_choice（属性 入口选择 AI/自己做、task_risk、alternatives_available 是否有替代路径）。采集端：入口分流埋点 + 季度意愿量表。
分层
任务类型 × 风险等级 × 用户使用时长。

S-06

中途接管成功率

TAKEOVER SUCCESS RATE标准卡
定义
用户中途接管后顺利完成任务且不丢已做工作的比例——人机协作的交接面。接管是用户对 AI 失去耐心的出口，接管体验差会直接放弃。
目的
用户接管后能否顺利继续完成任务——介入设计好坏的试金石。接管后要从头再来 = 介入机制形同虚设，用户会学会「别接，直接重开」。
公式
接管后顺利完成任务的次数 ÷ 接管总次数。与任务接管成本（时间 / 操作数）联读。
评估标准
健康 ≥80%预警 65–80%危险 <65%
数据来源
接管事件埋点 + 接管会话抽样。
数据埋点
事件 takeover（属性 trigger 不满意/想加速/风险规避、takeover_point 接管时点、state_handoff 交接完整性、completion 最终完成）。采集端：接管按钮埋点 + 接管后编辑轨迹追踪。
分层
接管时机（计划中确认点 / 用户主动打断）× 任务进行深度（前段 / 中段 / 尾段）。
