二
CHAPTER 02 · FULL CARDS

全卡 ×5：七维完整拆解

五张全卡是一条结算流水线：结果正确率是质量地基、结果可用率防止繁荣假象、首次交付通过率看一次做对、返工率算错了多贵、净价值实现率做最终结算——任务全部成功但净值为负，是 AI 产品最隐蔽的价值陷阱。

F-01

结果正确率

OUTPUT CORRECTNESS全卡 · 质量地基
定义
经核查判定正确的输出占比——质量地基。专防「看起来很专业的错误」：流畅、自信、有结构，但错了。
目的
回答「输出对不对」——质量的地基。不可用的对结果是浪费，可用的错结果是事故。它专门捕捉 AI 时代最危险的输出：看起来很专业的错误内容——流畅、自信、有结构，但错了。
公式
结果正确率 = 经核查判定正确的输出数 ÷ 核查输出总数。口径：「正确」需事前定义核查方式——事实核查（引用可溯）、测试验证（代码可跑）、专家评审（专业判断）三种口径分开统计，禁止混算。
评估标准
≥ 95% 健康85–95% 预警< 85% 危险
高风险场景（医疗 / 法律 / 资金）单列 ≥ 99%，且必须标注核查深度——抽样核查与全量核查的正确率不可比。
数据来源
核查流水（事实核查工具 + 单元测试结果）+ 专家抽样评审（每周固定）+ 用户负反馈回溯标注。
数据埋点
事件 verify_result（属性 method 事实核查/测试/专家评审、pass、error_type 事实/推理/过时、depth 核查深度）。采集端：核查工具流水 + 测试系统结果 + 周度专家抽样；幻觉高发区（数字 / 引用 / 时效内容）强制核查。
分层
输出类型 × 核查方式 × 风险等级。幻觉高发区（数字 / 引用 / 时效性内容）单独建层观察。
触发机制
某层正确率连续两周 < 85% → 冻结该类输出的自动交付，改为「必须人工核验」模式；高危场景任一错误 → 走安全域红线通道（卷三 S1）。
改进闭环
错误样本归因（事实错 / 推理错 / 过时信息）→ 对症修复（检索增强 / 知识更新 / 推理链约束）→ 核查回归 → 沉淀（错误样本入负例库；核查规则入质检规范）。
反指标
用「流畅度 / 字数」冒充质量——越自信的错越危险。gaming：只抽样易通过的输出核查。配对监控：核查覆盖率（漏检率）+ 用户纠错中「事实错误」占比。

F-02

结果可用率

USABLE OUTPUT RATE全卡
定义
输出无需重大修改即可使用的比例——区分「生成了」与「能用」。防止用生成量、字数、代码行数制造繁荣假象。
目的
区分「生成了」与「能用」。回答「用户拿到结果后，能否直接投入使用」——防止用生成量、字数、代码行数制造繁荣假象。
公式
结果可用率 = 无需重大修改即可使用的输出数 ÷ 总输出数。口径：「重大修改」= 用户改动超过输出量 30%，或改动核心结构 / 逻辑。微调措辞不算。
评估标准
≥ 85% 健康70–85% 预警< 70% 危险
数据来源
行为日志（用户编辑 diff：改动体量与位置）+ 显式反馈（「可直接使用 / 需修改」一键评价）+ 抽样评审（每周随机抽样人工判定校准）。
数据埋点
事件 edit_diff（属性 改动体量、改动位置 结构/局部、time_to_edit）、usability_vote（「可直接使用 / 需修改」一键）+ 周度人工抽判校准。采集端：编辑器 diff 埋点 + 反馈控件。
分层
输出类型（代码 / 文案 / 图表 / 文档）× 输出长度 × 任务类型——不同类型输出的可用率不可混算。
触发机制
某类输出可用率连续两周低于基线 10pp → 触发该类型的提示词 / 模型 / 模板专项优化；用户 diff 中「结构性改动」占比上升 → 触发输出格式与结构评审。
改进闭环
不可用样本归因（格式错 / 内容错 / 风格偏）→ 对症优化对应环节 → 观察 diff 体量下降 → 沉淀（典型失败输出入库为负例，用于评估集与 few-shot 校准）。
反指标
用「生成量 / 采纳率」冒充可用——采纳了再大改也算不可用。gaming：把「重大修改」阈值从 30% 放宽到 50% 让数据变好。配对监控：diff 结构性改动占比 + 首次交付通过率。

F-03

首次交付通过率

FIRST-PASS ACCEPTANCE RATE全卡
定义
首次交付即通过验收的任务占比——「一次做对」的能力，理解质量与交付质量的交汇点。
目的
回答「是否减少了返工」。衡量「第一次就把事做对」的能力——它同时反映理解质量与交付质量，是效率与质量的交汇点。
公式
首次通过率 = 首次交付即通过验收的任务数 ÷ 总交付任务数。口径：交付后 24h 内未收到修改请求且被使用，视为通过。
评估标准
≥ 75% 健康60–75% 预警< 60% 危险
数据来源
验收记录与修改请求日志 + 返工工单（关联原因分类）+ 交付物使用追踪。
数据埋点
事件 delivery（属性 first_pass_result、acceptance_within_24h、rework_reason 关联）。采集端：交付与验收日志关联 + 返工工单回链。
分层
交付类型 × 任务复杂度 × 验收方。不同验收人严格度不同，需校准后比较。
触发机制
某类任务通过率低于同类基线 15pp → 触发该类交付模板 / 流程 / 质检专项。
改进闭环
未通过原因三分类（理解偏差 / 质量不足 / 标准不清）→ 对症下药（强化澄清 / 交付前自检 / 标准前置到任务开始时）→ 验证 → 沉淀（交付 checklist 与验收标准库更新）。
反指标
用「交付及时率」冒充通过率——按时交付但被打回不算过。配对监控：返工率（互补面）+ 验收标准前置覆盖率（标准不清导致的误判）。

F-04

返工率

REWORK RATE全卡
定义
因不符合要求而重新执行的任务占比——价值漏损的显性出口，每次返工都是算力、时间、信任三重成本。
目的
回答「有多少活要重干」。返工是价值漏损的显性出口——每一次返工都是三重成本：AI 算力、用户时间、信任折损。与首次交付通过率互补：通过率看「一次做对的」，返工率看「错了之后多贵」。
公式
返工率 = 因不符合要求而重新执行或修改的任务数 ÷ 已交付任务总数。配套口径：返工成本比 = 返工消耗时长 ÷ 首次交付时长，衡量返工深度（小修 vs 推倒重来）。
评估标准
≤ 15% 健康15–30% 预警> 30% 危险
返工成本比 ≤ 0.3 健康（轻修补）；> 0.7 说明首版基本不可用，按推倒重来计。
数据来源
返工工单（关联原因分类）+ 编辑 diff 体量（结构性重写识别）+ 任务重复创建记录。
数据埋点
事件 rework_ticket（属性 cause 理解偏差/质量不足/标准不清/需求变更、depth 小修/重做、cost_ratio 返工/首版时长）。采集端：工单系统 + 编辑 diff 结构性重写识别 + 任务重复创建检测。
分层
返工原因（理解偏差 / 质量不足 / 标准不清 / 需求变更）× 交付类型 × 返工轮次。需求变更导致的返工不计入质量返工——分母要干净。
触发机制
某类任务返工率 > 30% → 触发「首版质量」专项；返工原因中「标准不清」占比上升 → 触发验收标准前置流程改造。
改进闭环
返工样本 → 根因三分类（理解偏差 / 质量不足 / 标准不清）→ 对症修复（强化澄清 / 交付前自检 / 标准前置）→ 验证返工率下降 → 沉淀（返工原因库更新；高频返工模式写入交付 checklist）。
反指标
用「返工完成快」冒充质量可控——返得快也是返了。gaming：把质量返工记为需求变更。配对监控：返工原因分布（结构健康度）+ 净价值实现率。

F-05

净价值实现率

NET VALUE REALIZATION全卡 · 最终结算
定义
扣除使用、核验、返工成本后的净收益与毛收益之比——最终结算科目。防「任务全成功但净值为负」的隐蔽陷阱。
目的
结果与价值的最终结算科目。回答「扣掉所有成本后，用户到底赚没赚」——任务收益减去使用成本、核验成本、返工成本。它是防「高成功率假象」的终极指标：任务全部成功但净值为负，是 AI 产品最隐蔽的价值陷阱。
公式
净价值实现率 = (任务收益 − 使用成本 − 核验成本 − 返工成本) ÷ 任务收益。体验账本 VOL.03 净值率 NEV 口径同源：NEV > 1 才是正向体验。收益按时间节省 + 质量增益折算，成本按人力时薪折算。
评估标准
> 1.2 健康1.0–1.2 存疑< 1.0 负价值
任何任务类净值率 < 1 持续一个月，应评估下线该场景入口。
数据来源
收益-成本台账（时间节省实测 + 质量增益评估）+ 成本三明细（提示撰写 / 核验时长 / 返工时长）+ 基线库对照。
数据埋点
事件 value_ledger（属性 gain 时间节省 + 质量增益折算、cost_use/cost_verify/cost_rework 三明细、baseline_ref 基线引用）。采集端：时间戳台账 + 成本三明细埋点 + 基线库对照；月度结算。
分层
任务类型 × 用户熟练度 × 时间窗。净值率有爬坡效应——新用户的核验成本天然高，按熟练度分层后才看得清真实价值。
触发机制
净值率环比下降 > 0.15 → 触发成本三明细拆解，定位是核验涨了还是返工涨了；新场景上线 90 天净值率 < 1 → 触发场景价值复审。
改进闭环
负净值场景归因 → 收益端提质 or 成本端降耗（核验自动化 / 交付前自检降返工）→ 重算验证 → 沉淀（场景价值基线表更新；「不划算场景清单」进入产品决策）。
反指标
用「任务成功率」冒充价值——成功不等于划算。gaming：漏记核验成本（最大隐性成本）。配对监控：核验时长占比 + 「不划算场景清单」命中率。

CHAPTER 03 · STANDARD CARDS

标准卡 ×3：验收的三个切面

三张标准卡是验收的三个切面：结果完整率查「全不全」、用户验收率要「签字画押」、质量改善幅度比「比基线好多少」——没有基线对照的质量叙事都是自嗨。

S-01

结果完整率

OUTPUT COMPLETENESS标准卡
定义
输出满足全部必要交付要求的比例——「对」还不够，「全」才算完。遗漏逼用户做「补件」。
目的
交付物是否满足全部必要交付要求——「对」还不够，「全」才算完。遗漏前置说明、缺关键段落、少必填字段的输出，都逼用户做「补件」。
公式
结果完整率 = 满足全部必要交付要求的任务数 ÷ 总任务数（验收 checklist 预埋检查点逐项判定）。
评估标准
≥ 90% 健康80–90% 预警< 80% 危险
遗漏项按「阻塞性 / 非阻塞性」分记——阻塞性遗漏直接计危险。
数据来源
验收 checklist 判定 + 用户补件行为识别（追加指令 / 手动补全）。
数据埋点
事件 checklist_verify（属性 检查点逐项 pass/fail、blocking 阻塞性遗漏）、patch_action（用户补件行为：追加指令 / 手动补全）。采集端：验收 checklist 钩子 + 补件行为识别。
分层
交付类型 × 遗漏类型 × 任务复杂度。

S-02

用户验收率

USER ACCEPTANCE RATE标准卡
定义
用户显式接受最终结果的任务占比——价值的「签字画押」，行为推断（可用率）的显式对照面。
目的
用户明确接受最终结果的任务比例——验收是价值的「签字画押」。与结果可用率的区别：可用率由行为 diff 推断，验收率由显式动作确认；二者背离时说明行为推断有偏差。
公式
用户验收率 = 明确接受的任务数 ÷ 需验收任务总数。口径：「明确接受」= 点击接受 / 复制导出 / 直接使用下游。
评估标准
≥ 85% 健康70–85% 预警< 70% 危险
验收后 24h 内又返工的「假验收」单独追踪。
数据来源
验收动作埋点 + 验收后行为追踪（真用 / 弃用）。
数据埋点
事件 acceptance_action（属性 accept/copy_export/downstream_use 接受方式）、post_accept_rework（24h 内反悔）。采集端：验收动作埋点 + 验收后行为追踪。
分层
任务类型 × 验收方 × 风险等级。

S-03

质量改善幅度

QUALITY IMPROVEMENT标准卡
定义
AI 辅助结果相对传统基线的质量增益——「不比人差」不够，要答「好多少」。
目的
AI 辅助结果与传统方式结果的质量差异——「不比人差」是不够的，必须回答「比基线好多少」。没有基线对照的质量叙事都是自嗨。
公式
质量改善幅度 = (AI 辅助结果质量分 − 基线结果质量分) ÷ 基线质量分。质量分来自专家盲评（A/B 混排，评审者不知来源）。
评估标准
≥ +15% 显著0 – +15% 边际< 0 负改善
盲评一致性（评审者间信度）≥ 0.7，否则数据不可信。
数据来源
对照实验（同类任务双轨执行）+ 专家盲评 + 历史基线库。
数据埋点
事件 blind_review（A/B 混排盲评分，属性 维度 准确/深度/结构/风格、信度 评审者间一致性）。采集端：对照实验双轨执行 + 月度盲评。
分层
任务类型 × 质量维度（准确 / 深度 / 结构 / 风格）。

CHAPTER 04 · LITE CARDS

简卡 ×1：三要素速览

简卡结果相关性守最后一道门：内容没错，但要与用户目标和当前情境相关——防止「答非所问的正确」。

L-01

结果相关性

OUTPUT RELEVANCE简卡
目的
输出与用户目标和当前情境的相关程度——防止「答非所问的正确」：内容没错，但与要办的事无关。
公式与阈值
